# CXA `<HeroHoodie />` — Interactive 3D Hoodie Component

A reusable Next.js/React component package for a premium, rotating, branding-aware
3D hoodie hero. Built to be dropped into the existing CXA homepage as
`<HeroHoodie />` — this package does not build any part of the homepage itself.

**Read this first, in order:** §1 (recommended approach & why), §2 (what's built
vs. what you still need), then `hoodie-model-spec.md` if you're the one sourcing
the garment asset.

---

## 1. Recommended technical approach

**Real WebGL 3D (react-three-fiber / drei), not an image sequence.** You asked
for this explicitly, and it's the right call for this brief: the rotation needs
to be continuous and scroll-scrubbable in both directions, branding needs to
attach to specific surfaces at arbitrary angles (not just at whatever few
angles happen to have a photo), and "premium automotive configurator" is a
description of a *real 3D renderer's* look (specular response, consistent
lighting as the object turns, geometry-accurate occlusion) — a crossfading
photo sequence can approximate the first requirement passably and fails the
other two outright. It's also the only approach that satisfies your explicit
instruction not to fake rotation from unrelated flat images.

The cost of this approach is that it needs an actual 3D asset (a GLB), which
this package cannot generate — see §2.

**Library choice:** `@react-three/fiber` (React renderer for three.js) +
`@react-three/drei` (helpers: `useGLTF`, `Decal`, `Environment`,
`ContactShadows`, `PerspectiveCamera`). This is the standard, well-maintained
stack for exactly this kind of product-configurator UI in React, and its
`Decal` component is a genuine projected-texture decal (wraps to the
underlying surface curvature) rather than a flat plane glued on top — the
right primitive for garment branding.

## 2. What's built now vs. what you need to provide

### Built now (in this package)

- The entire `<HeroHoodie />` component: rotation engine (drag/touch/keyboard/
  programmatic/scroll), branding-zone architecture, accessibility, SSR
  handling, WebGL-fail and reduced-motion fallbacks, performance scaffolding.
  All of it is real, working code, not a stub.
- A **placeholder GLB** (`public/models/cxa-hoodie-placeholder.glb`,
  generated by `scripts/generate_placeholder_glb.py`) built from simple
  grey primitives. It exists purely so the component above can actually be
  run, dragged, scrolled through, and have branding decals verified today,
  before a real garment model exists. It is explicitly, unmistakably not a
  garment render (mid-grey material named `DEV_PLACEHOLDER_DO_NOT_SHIP`) —
  see `scripts/placeholder-preview-front.png` / `-back.png` for exactly what
  it looks like (a labeled wireframe render with the branding anchors marked
  as red dots) before relying on any description of it here. **Do not ship
  this to production.** It satisfies the exact same node-naming contract the real
  asset must (§3 below / `hoodie-model-spec.md`), so swapping it out is a
  one-line change (`DEFAULT_MODEL_SRC` in `hoodie-config.ts`), not a
  rewrite.
- Default demo branding (`public/branding/`) reusing the CXA logo crops
  already cut from your reference hero photograph — left chest + a vertical
  sleeve treatment, applied via the exact same runtime decal system the
  final artwork will use.
- Flat-image fallback photography (`public/hoodie-fallback/`, also from the
  same reference photograph) for the no-WebGL / model-load-failure /
  reduced-motion paths.

### What you need to provide

**A production GLB of the actual hoodie** (`public/models/cxa-hoodie.glb`).
This package cannot generate that — I don't have 3D modeling or
photogrammetry tooling available, and turning 2D reference photos into an
accurate rotatable 3D garment mesh isn't something that can be approximated
without misrepresenting the result as more real than it is (which you
explicitly asked me not to do).

The full, exact specification — coordinate system, scale, required node
names for both the mesh parts and the branding anchors, materials, geometry
budget, export settings, file-size target — is in **`hoodie-model-spec.md`**.
Hand that file directly to whoever models the garment (in-house artist,
freelancer, or a 3D/photogrammetry vendor). As long as the delivered GLB
matches that node-naming contract, integration is: drop the file into
`public/models/`, update one constant, done — no component code changes.

If in the meantime you want a closer-to-final placeholder for stakeholder
review (rather than the grey dev primitive), the cheapest path is
commissioning a low/mid-poly stylized hoodie from a 3D marketplace (Sketchfab,
CGTrader, TurboSquid have black-hoodie assets) and having someone add the 8
`Anchor_*` empties per the spec — much less work than modeling from scratch,
and it's still swappable for the true custom asset later without touching
code.

## 3. Component architecture

```
components/hero-hoodie/
  HeroHoodie.tsx            Public entry point ("use client"). SSR-safe mount
                             gate, WebGL detection, reduced-motion handling,
                             error boundary wiring, accessible wrapper +
                             live region + prev/next controls.
  HeroHoodieCanvas.tsx       The R3F <Canvas>: camera, lighting rig,
                             Environment (reflections only, transparent bg),
                             ContactShadows, Suspense boundary. Dynamically
                             imported with ssr:false — this file, and
                             everything it imports, never reaches the server
                             bundle or a WebGL-unsupported client.
  HoodieModel.tsx            Loads the GLB (useGLTF), resolves each
                             configured branding zone's anchor -> mesh-local
                             transform, drives the per-frame rotation damping
                             + active-position derivation, renders the
                             branding decals.
  BrandingDecal.tsx           One <Decal> + texture load, Suspense-wrapped per
                             zone so one slow/broken asset can't block the rest.
  HeroHoodieErrorBoundary.tsx  Class component; catches model-load/render
                             errors, swaps in the static fallback image.
  HoodieFallbackImage.tsx     The static-photo fallback (next/image, priority).
  useHoodieRotation.ts        All rotation state + interaction logic: the
                             shared ref the render loop reads, drag/touch/
                             keyboard handlers, the imperative controller
                             (goToPosition/next/previous/setRotationProgress).
  useReducedMotion.ts         prefers-reduced-motion, live-updating.
  useWebGLSupport.ts          Cheap canvas-based WebGL feature detect.
  hoodie-types.ts              All public types. No three.js/R3F imports --
                             safe to import from a server component.
  hoodie-config.ts             Every tunable number: rotation keyframes,
                             camera, lighting, zone->anchor map, drag feel,
                             default asset paths. The file you'll actually
                             edit most.
  hoodie-math.ts               Pure functions (angle interpolation, circular
                             damping, position lookup) -- no React/three
                             imports, trivially unit-testable.
  index.ts                     Barrel export.
public/
  models/cxa-hoodie-placeholder.glb   Dev placeholder -- see §2.
  branding/                    Default demo logo artwork.
  hoodie-fallback/              Default demo fallback photography.
scripts/
  generate_placeholder_glb.py  Regenerates the placeholder GLB.
example/
  HomepageExample.tsx           Reference scroll-integration code (not part
                             of the component itself -- copy what's useful).
hoodie-model-spec.md            Full 3D-asset spec for the production GLB.
```

Nothing in `components/hero-hoodie/` imports anything from the rest of a CXA
app, and the component takes no dependency on routing, layout, or any other
homepage code — it's a self-contained unit that only talks to its parent
through props and the two callback/ref APIs described below.

## 4. Dependencies

Add to the existing app's `package.json`:

```json
{
  "dependencies": {
    "three": "^0.185.0",
    "@react-three/fiber": "^9.7.0",
    "@react-three/drei": "^10.7.8"
  },
  "devDependencies": {
    "@types/three": "^0.185.0"
  }
}
```

These versions are the ones that support React 19 (`@react-three/fiber` v9 and
`@react-three/drei` v10 are the first majors of each that target React 19 —
their v8/v9 predecessors are pinned to React 18 and will not install cleanly
against React 19 peer deps). Since `@react-three/fiber@^9.7.0`'s own peer
range is `react >=19 <19.3`, check that range against whatever exact React 19
patch the rest of the app is on when you do the real install, and widen/pin as
needed — that upper bound is the one version detail here worth re-verifying at
install time rather than trusting this document, since it'll keep moving.

No other runtime dependency is required — no animation library, no gesture
library. Drag/scroll/keyboard interaction is hand-rolled in
`useHoodieRotation.ts` (see §12, it's a deliberately small amount of code) to
avoid pulling in a dependency for something this contained.

## 5. Using the component

```tsx
import { HeroHoodie } from "@/components/hero-hoodie";

<div style={{ height: "80vh" }}>
  <HeroHoodie />
</div>
```

That's the entire minimal integration — it ships with sensible defaults
(placeholder model, demo branding, demo fallback image) and will render,
rotate on drag, and respond to `rotationProgress` if you pass it. The parent
is responsible for giving it a sized container (explicit height, or an
aspect-ratio box) — the component fills 100%/100% of whatever it's given and
does not impose a size itself, so there's no layout shift regardless of what
size the homepage design ultimately wants.

### Scroll-driven rotation

See `example/HomepageExample.tsx` for two complete, working integration
patterns:

1. **React-state-driven** (`rotationProgress` prop) — compute a 0..1 scroll
   fraction and pass it down; simplest, fine for most pages.
2. **Imperative rAF-driven** (`controllerRef.current.setRotationProgress()`)
   — updates the rotation ref directly from a scroll/rAF loop with zero React
   re-renders per scroll pixel. Reach for this if profiling shows jank from
   approach 1, or if the homepage already runs its own rAF loop for other
   scroll effects and you want everything on one tick.

Both talk to the exact same underlying rotation engine — mix and match freely,
switch later without restructuring anything.

### Branding

```tsx
<HeroHoodie
  branding={{
    leftChest: "/branding/customer-logo-chest.png",
    leftSleeve: { src: "/branding/customer-logo-sleeve.png", scale: 1.1 },
    fullBack: "/branding/customer-print-back.png",
  }}
/>
```

Omit a zone and nothing renders there. Artwork should be a transparent PNG/
WebP for a clean decal result — see `hoodie-model-spec.md` §4 for the
material context it's projected onto. The 8 available zone keys are listed in
`hoodie-types.ts` (`BrandingZoneKey`) and match the spec's zone list exactly
(`leftChest`, `rightChest`, `centreFront`, `fullFront`, `upperBack`,
`fullBack`, `leftSleeve`, `rightSleeve`).

### Reading the active branding position

```tsx
<HeroHoodie onPositionChange={(position) => setLabel(position)} />
```

`position` is one of the six values from the spec's callout list (`FRONT`,
`LEFT_CHEST`, `LEFT_SLEEVE`, `FULL_BACK`, `RIGHT_SLEEVE`, `RIGHT_CHEST`). The
component renders no visible typography of its own for this — it's a data
callback only, so the homepage's own HTML/CSS callouts stay entirely in the
homepage's design system, per the spec's explicit instruction not to bake
site typography into the 3D layer.

### Full prop reference

See the JSDoc in `hoodie-types.ts` (`HeroHoodieProps`) — every prop is
documented there inline; this README doesn't duplicate it to avoid the two
copies drifting apart. Quick summary of the props most integrations will
touch: `branding`, `rotationProgress`, `onPositionChange`, `controllerRef`,
`interactive`, `showControls`, `showShadow`, `reducedMotion`, `modelSrc`,
`fallbackImageSrc`, `className`, `ariaLabel`.

## 6. Scroll-control API

Covered in §5 above and demonstrated fully in `example/HomepageExample.tsx`.
In short: `rotationProgress` (prop) or `controllerRef.current.setRotationProgress()`
(imperative) both drive the same 0..1 timeline defined in `hoodie-config.ts`'s
`ROTATION_KEYFRAMES`, which encodes the exact scroll narrative from the spec
(0% FRONT → 15% LEFT_CHEST → 30% LEFT_SLEEVE → 50% FULL_BACK → 70%
RIGHT_SLEEVE → 85% RIGHT_CHEST → 100% FRONT). The homepage controls *when*
that timeline advances (by computing scroll progress however it likes); the
component owns *how* it looks (smoothing, direction, easing).

`controllerRef.current` also exposes `goToPosition(position, { animate })`,
`next()`, `previous()`, and `getActivePosition()` for non-scroll programmatic
control (e.g. clickable position chips elsewhere on the page).

---

## 7. Branding-zone architecture

Covered in §5 and in full technical detail in `hoodie-model-spec.md` §3. The
short version: each zone is a named empty ("anchor") in the GLB; at runtime
`HoodieModel.tsx` resolves that anchor's world transform relative to its
target mesh and hands it to a `<Decal>`, so artwork is never baked into the
base garment texture — it's applied fresh on every render from whatever
`branding` prop the homepage passes in, including nothing at all. This is
what lets the existing CXA artwork-upload system supply logos later without
touching this component.

---

## 8. Desktop interaction

Pointer-event drag (mouse), with light inertia after release; `ArrowLeft`/
`ArrowRight` when the component has keyboard focus; the built-in prev/next
buttons; and, of course, `rotationProgress`/scroll. All of these write into
the same rotation state, so they compose naturally (e.g. scroll sets the base
angle, a drag mid-scroll takes over until the next scroll update arrives).

---

## 9. Mobile fallback

Touch drag works identically to mouse drag (unified via the Pointer Events
API — no separate touch-event code path to maintain). The wrapper uses
`touch-action: pan-y`, so vertical page-scrolling gestures pass through
untouched and only horizontal drag is captured for rotation — this was a
deliberate choice so the scroll-driven experience (the primary interaction
per the spec) is never fought by the component on touch devices.

For genuinely low-powered devices, `interactive={false}` disables drag/
keyboard entirely (scroll-driven rotation still works, it's the cheapest
interaction path), and `reducedMotion` (see next section) gives a fully
static fallback.

---

## 10. Reduced-motion behavior

`prefers-reduced-motion: reduce` is honored automatically (live — it updates
if the OS setting changes mid-session) and can be overridden with the
`reducedMotion` prop. When active: the garment snaps (no animation) to a
fixed three-quarter angle (`LEFT_CHEST`, 20°) chosen specifically because it
reads as a strong, informative product shot on its own — hood, sleeve, and
chest branding all visible at once — so understanding the garment never
depends on anything moving. Scroll/drag stop affecting rotation; the prev/
next buttons remain available for discrete (instant, non-animated) exploration.

---

## 11. WebGL fallback

Two independent safety nets, both landing on the same `HoodieFallbackImage`:
a pre-flight `useWebGLSupport()` check (skips even attempting to load the R3F/
three bundle if WebGL2/WebGL1 aren't available, which also saves that JS
payload entirely for those visitors), and a `HeroHoodieErrorBoundary` around
the canvas subtree that catches a bad/missing GLB or a mid-session WebGL
context failure. The hero is never left empty.

## 12. Performance considerations

- **Code-splitting:** the entire R3F/three bundle is behind
  `next/dynamic(..., { ssr: false })` in `HeroHoodie.tsx`. Visitors who get
  the fallback image (no WebGL, or reduced motion with `interactive=false`)
  never download that JS at all.
- **Zero-re-render rotation:** rotation state lives in a plain ref
  (`RotationState`), read/written every frame inside `useFrame` and from raw
  DOM pointer handlers — never through `setState`. Scroll-linked rotation via
  `controllerRef.setRotationProgress()` follows the same rule. This is the
  single biggest lever against scroll jank for a WebGL element on an
  above-the-fold hero, and it's why the API has both a prop and an
  imperative path (§6).
- **Geometry/texture budget:** specified in `hoodie-model-spec.md` (15–30k
  triangles, 2K textures, Draco compression, target <3–5MB total). The
  placeholder GLB is 24KB — the real budget only becomes relevant once the
  production asset lands, but it's specified now so whoever models it isn't
  guessing.
- **Contact shadow:** baked once (`frames={1}` in `HeroHoodieCanvas.tsx`)
  rather than recomputed every frame, trading a shadow that doesn't
  perfectly track the spin for meaningfully less per-frame GPU work. Bump
  `frames` in `hoodie-config.ts`'s usage if that trade ever looks wrong in
  review — it's a one-line change.
- **`dpr={[1, 2]}`** caps device-pixel-ratio rendering at 2x — prevents
  needlessly rendering at 3x/4x on very high-density phones for marginal
  visual gain and real GPU cost.
- **Suspense per branding decal:** one slow-loading logo image can't block
  the base garment (or the other zones) from appearing.
- Nothing here needs KTX2/Meshopt tooling wired into the *component* — those
  are asset-export-time choices for whoever produces the GLB (spec'd in
  `hoodie-model-spec.md` §4–5), not something the runtime code needs to know
  about.

## 13. Next.js integration notes

- Every file that touches React state, refs, or the DOM is marked
  `"use client"`. `HeroHoodie.tsx` is the client/server boundary — import it
  from a Server Component homepage page freely, e.g.:

  ```tsx
  // app/page.tsx (Server Component, unchanged)
  import { HeroHoodie } from "@/components/hero-hoodie";

  export default function HomePage() {
    return (
      <main>
        <section style={{ height: "80vh" }}>
          <HeroHoodie />
        </section>
        {/* rest of the existing homepage, untouched */}
      </main>
    );
  }
  ```

  This does **not** make the homepage a client component — only the hoodie
  subtree is client-rendered, exactly as it would be for any other
  interactive island.

- The heavy WebGL bundle is additionally dynamically imported *inside*
  `HeroHoodie.tsx` (see §12), so there's no need to also wrap the
  `<HeroHoodie />` import itself in `next/dynamic` at the call site — it's
  already handled internally. (Doing so anyway is harmless if you'd rather
  be explicit about it at the page level.)
- SSR renders the same loading-skeleton markup the client renders before
  mount, so there's no hydration mismatch warning and no content flash.
- Model and image assets are served from `public/` the standard Next.js way
  — no custom loader or `next.config.js` changes required. If the app's
  `next/image` config restricts `domains`/`remotePatterns`, note that the
  fallback image uses `next/image`, so a same-origin `public/` path (the
  default here) needs no config changes at all.

## Verifying this package before integrating

1. `npm install` the dependencies from §4 into the real app (or a scratch
   Next.js 16 app for a quick smoke test).
2. Copy `components/hero-hoodie/`, `public/models/`, `public/branding/`,
   `public/hoodie-fallback/` in.
3. Drop `<HeroHoodie />` onto any page and confirm: it renders the grey
   placeholder garment; drag rotates it; the two default branding decals
   (chest + sleeve) appear roughly in the right places on the placeholder's
   torso/sleeve; the prev/next buttons step through named positions; toggling
   "reduce motion" in OS accessibility settings snaps it static.
4. Regenerate the placeholder any time with
   `python3 scripts/generate_placeholder_glb.py` (requires
   `pip install trimesh pygltflib`) — useful for testing anchor-placement
   changes before they go into the real GLB spec.
5. When the production GLB is ready, follow `hoodie-model-spec.md` §8.
